# Touch attribution fix ("my own taps on the overlay do nothing")

## Diagnosis: touch always reached the window

Real-finger taps produced a full input trace: `win:down/move/up`, `dev=5` (real touchscreen), 54–77 events, none lost. The input path was fine — the bug was in **event attribution**.

## Three actual bugs

1. **The root node's `GestureController` was overwritten.** `drag_window` and window-level logging both called `root.setOnTouchListener(...)`, competing with root-node gestures for the same slot. The floating ball *is* the root node, so its `on:{click}` never fired — the finger landed, the ball flashed, no event. Fix: when the root node has `on`, no other touch listener is attached (window dragging goes through `drag:*` events instead).

2. **Child nodes ignored `gravity`.** The label inside the ball was drawn at the window's top-left corner, *outside* the circle. Hit areas follow the text, so the visible circle contained no clickable node — and `overlay.tree` reported the tiny label's coordinates. That is the physical explanation for "AI can click it, I can't".

3. **Nodes without `on` swallowed touches.** Text nodes attached gestures unconditionally, eating clicks that should have bubbled to the container. Now only nodes declaring `on` handle gestures.

## Added

- `overlay.show` accepts `"trace":true` — window-level touches (`win:down/move/up`) are written to the event stream, no logcat needed:

  ```bash
  tbridge-overlay events 0
  ```

- `dev=-1` marks injected events (`input tap`); positive values are real touchscreen input. Diagnostic rule of thumb: **window receives no events → input path; events arrive but no `click` → attribution.**

## Compatibility

- Nodes without `on` no longer report clicks (previously they did, bubbling to the parent).
- `drag_window` is ignored when the root node has `on`.
