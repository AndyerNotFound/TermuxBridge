# Gesture recognition rewrite / measured drag performance

## Gesture recognition

Previously there was only a fixed 500 ms long-press, drag and clickable were mutually exclusive, and `ACTION_CANCEL` did not reset state. All parameters are now configurable per node:

| Parameter | Default | Meaning |
|---|---|---|
| `tap_ms` | 280 | Multi-tap window (max gap between taps) |
| `hold_ms` | 500 | Long-press trigger time |
| `long_hold` | off | Second-stage long-press event after hold_ms |
| `slop` | 20dp | Movement that enters dragging |
| `swipe` | 56dp | Minimum travel for a swipe |

Events: `click` / `double` / `triple` / `long` / `long_hold` / `drag:start|move|end|cancel` / `swipe:up|down|left|right`, all carrying `dev` (-1 = injected, positive = real touchscreen).

- **Drag and click coexist**: with `drag_window:true` the window follows the finger while drag events are still reported; tap still works after release.
- **`ACTION_CANCEL` synthesizes `drag:end`**: an interrupted drag no longer leaves the controller stuck.
- **Fast swipes emit `drag:cancel` first**, then `swipe:*` — treat cancel as "drag aborted".

## Drag performance (measured, not estimated)

```bash
tbridge overlay stats
{"commits":279,"avg_commit_ms":0.06,"max_commit_ms":0.26,
 "frame_gap_p50_ms":16.59,"frame_gap_p95_ms":17.20,"fps_est":60}
```

- `updateViewLayout` averages **0.06 ms** — layout is not the bottleneck.
- Commit interval p50 = 16.6 ms → a steady 60 fps; that is the ceiling of the window-repositioning path, not a code issue.
- During drags the root view uses `LAYER_TYPE_HARDWARE` (moves only reposition a cached texture).
- Added `"hz":120` (`preferredRefreshRate`); measured: the system still delivers touch at 60. Kept as a parameter.

## Verification matrix

Injected (`dev=-1`): tap / double / triple / long(500) / `hold_ms:150` / `long_hold:1200` / drag / swipe:right / drag_window moving the window / tap after moving.
Real finger (`dev=5`): click on `id=ball`, window follows the drag, ball dims to translucent.
